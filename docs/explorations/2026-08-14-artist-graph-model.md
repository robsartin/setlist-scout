# Exploration: an artist-relationship graph model

Date: 2026-08-14
Status: Exploration (spike #104) — no code changes. Basis for a go/no-go decision.

## 1. The idea, and why it might be worth it

Today, when expansion discovers a candidate artist, the only record of *why* is three flat
columns on the `Artist` row itself: `source` (`MEMBER_EXPANSION` / `SIMILAR_EXPANSION` /
`TRIBUTE_EXPANSION`), `discoveredVia` (the base artist's *name*, a plain string, not a foreign
key), and `note` (free text like `"member/lineup relation of Radiohead"`). See
`catalog/Artist.java:29-33`.

That's a **one-hop breadcrumb**, not a relationship model:

- It's a name string, not a link — there's no `Artist` row it actually points to, so you can't
  join from a candidate back to the base artist's own row, only re-search by name.
- It's **overwritten** if the same artist is discovered a second time via a different source.
  `CandidatePersistenceListener.on()` (`catalog/CandidatePersistenceListener.java:42`) checks
  `existsByOwnerAndNameIgnoreCase` and returns early — the *second* discovery is silently
  dropped, including its `source`/`note`. If Radiohead's members surface Thom Yorke via
  MusicBrainz and Last.fm both independently suggest him as "similar," only whichever event
  lands first is recorded; the corroborating second source is thrown away entirely.
- It can't answer "how is X related to Y" beyond a single hop, and can't be traversed at all —
  there's no query that walks from a seed outward through its discovered network.

A **graph model** makes the relationship itself a first-class row: a typed edge
`(from_artist) —[classification]→ (to_artist)`, carrying who asserted it (`source` id, e.g.
`musicbrainz`, `lastfm`, `tribute-llm`), why (`note`), and when. Multiple assertions of the same
edge become multiple edges (or a strengthened single edge), not silent loss.

**Why it might be worth it**, mapped to the current code:

- **Provenance / explainability.** "Why is this band in my candidates?" today is one `note`
  string that can be stale or missing (overwritten by dedup). A graph gives the actual assertion
  history: every source that ever connected two artists, with its own note and timestamp.
- **Dedup relationships, not just artists.** The `existsByOwnerAndNameIgnoreCase` short-circuit
  in `CandidatePersistenceListener` exists because `Artist` conflates "is this a person/band we
  know about" with "how did we find it" — one row, one provenance. A graph separates those: the
  *node* (artist) is deduplicated once; the *edge* (this specific relationship assertion) is not,
  and corroboration from a second source becomes additional signal instead of a discarded event.
- **Traversal / ranking.** `RelationSource` and `ExpandUnitRunner` today only ever go one hop
  from a `PENDING_REVIEW`/`SEED`/`APPROVED` artist outward (`ExpandUnitRunner.run`,
  `expansion/ExpandUnitRunner.java:47-72`). A graph is what "bands connected to X within 2 hops"
  or "reachable from N seeds = rank higher" would actually be built on — recursive CTEs over an
  edge table give this for free; the current flat-column model cannot express it at all.
- **Avoid re-asking a source.** `expand_job` already tracks one row per `(owner, artistId,
  source)` (ADR-0023) — it prevents re-querying the *same* base artist/source pair, but it can't
  tell you "we already know Radiohead ↔ Thom Yorke is a member edge" if the discovery came from a
  different direction (e.g. querying Thom Yorke's own MusicBrainz page). An edge table with a
  `(from, to, type)` lookup could short-circuit that.
- **UI.** `review/CandidateGroups.java` already groups the Candidates page by base-artist
  (`discoveredVia`) × relation type (`source`) — that's already graph-shaped output being
  assembled from flat columns via a `GROUP BY`. A real edge table is the natural backing store for
  that exact view, and opens the door to an actual "related bands" graph visualization later.

This is a genuinely reasonable motivation. The question below is whether the payoff justifies the
model and migration cost at this app's current scale and feature set.

## 2. Storage options + tradeoffs

### (a) Relational edge table in the existing Postgres — **recommended**

```sql
CREATE TABLE artist_edge (
    id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    owner         varchar(255) NOT NULL,
    from_artist_id bigint NOT NULL REFERENCES artist(id),
    to_artist_id   bigint NOT NULL REFERENCES artist(id),
    type          varchar(255) NOT NULL,   -- MEMBER_OF / TRIBUTE_OF / SIMILAR_TO / ...
    source        varchar(255) NOT NULL,   -- RelationSource#id(): "musicbrainz","lastfm","tribute-llm",...
    note          text,
    weight        double precision,
    created_at    timestamptz NOT NULL,
    CONSTRAINT artist_edge_unique UNIQUE (owner, from_artist_id, to_artist_id, type, source)
);
CREATE INDEX artist_edge_from_idx ON artist_edge (owner, from_artist_id);
CREATE INDEX artist_edge_to_idx   ON artist_edge (owner, to_artist_id);
```

Traversal ("everything within N hops of artist X") is a standard recursive CTE:

```sql
WITH RECURSIVE reachable(artist_id, depth) AS (
    SELECT :startId, 0
    UNION ALL
    SELECT e.to_artist_id, r.depth + 1
      FROM artist_edge e
      JOIN reachable r ON e.from_artist_id = r.artist_id
     WHERE r.depth < :maxDepth AND e.owner = :owner
)
SELECT DISTINCT artist_id, min(depth) FROM reachable GROUP BY artist_id;
```

**Tradeoffs:**
- Fits the existing stack exactly: same Postgres instance, same Flyway migration story
  (ADR-0020), same JPA/Spring Data repository pattern every other table in this app uses, same
  backup/ops story (Render-hosted Postgres, no new infra).
- Recursive CTEs handle the depths this app plausibly needs (2-3 hops) without strain, and are
  ordinary SQL a future maintainer (or Claude, next session) can read without learning a new
  query language.
- The dataset is small — per-owner artist counts in the hundreds to low thousands, edge counts a
  small multiple of that. Postgres indexes on `(owner, from_artist_id)` / `(owner, to_artist_id)`
  handle this trivially; there's no scale pressure pushing toward a specialized engine.
- Downside: deep/variable-depth traversal (5+ hops, shortest-path, centrality/community-detection
  algorithms) gets awkward in SQL. Not a concern here — nothing in the issue or the current
  feature set calls for that.

### (b) Postgres + Apache AGE

Apache AGE bolts openCypher graph queries onto Postgres as an extension, operating on the same
underlying storage.

**Tradeoffs:**
- Same physical database, so no new hosting/backup story — but it *is* a new extension to
  install, keep patched, and reason about, on a hosting platform (Render) whose managed Postgres
  offering would need to support installing it (worth confirming before ever considering this
  seriously — not confirmed as part of this spike).
- Buys expressive Cypher traversal syntax over what a recursive CTE already does adequately at
  this scale. The win is developer ergonomics for *complex* graph queries — this app doesn't have
  those yet.
- Adds a second query language/mental model to a single-purpose Spring Boot app that otherwise
  has zero non-JPA/SQL surface. That's real cost for a benefit this app doesn't currently need.
- **Verdict: not justified.** Revisit only if traversal queries actually become painful in plain
  SQL — they haven't been written yet, so that's speculative.

### (c) Dedicated graph database (Neo4j)

**Tradeoffs:**
- Genuinely the right tool if this were a large-scale, graph-native product (social network,
  recommendation engine at scale) — full Cypher, graph algorithms (PageRank, community detection,
  shortest path) out of the box, purpose-built storage/indexing for traversal.
- For this app: a second database to run, back up, and pay for (or self-host) alongside Postgres;
  a second connection pool, a second ORM/driver, a second migration story, a second thing to keep
  in sync if any data needs to live in both places (it would — search/show data has nothing to do
  with the artist graph and has no reason to move).
- Artist/edge counts here (single-digit users, hundreds to low thousands of artists per owner)
  are nowhere near where Neo4j's advantages start to matter.
- **Verdict: clear overkill**, noted per the issue's ask but not a serious contender.

**Recommendation: (a), the relational edge table.** It's a strict evolution of the existing
schema/stack, costs one Flyway migration, and everything the issue's "why it might be worth it"
section asks for (provenance, dedup, 2-3 hop traversal, avoid re-asking a source, backing the
grouped Candidates UI) is achievable with plain SQL at this scale.

## 3. How it fits the current design

### Edge = "(base artist) —[classification]→ (discovered artist), asserted by (source), note"

This maps directly onto what already exists. `RelationSource` (`expansion/source/RelationSource.java`)
already has exactly the right shape:

```java
public interface RelationSource {
    String id();                                  // -> artist_edge.source
    List<String> related(String artistName);       // -> discovered names (to be resolved to to_artist_id)
    ArtistSource classification();                 // -> artist_edge.type
    String note(String baseArtist);                // -> artist_edge.note
    default boolean appliesTo(ArtistStatus status) { return true; }
}
```

`ExpandUnitRunner.run` (`expansion/ExpandUnitRunner.java:47-72`) is the one place that turns a
`RelationSource` result into `CandidateDiscovered` events. Emitting edges would extend, not
replace, this method:

```java
// sketch, not committed code
for (String name : related) {
    if (name == null || name.isBlank()) continue;
    transactionTemplate.executeWithoutResult(status -> publisher.publishEvent(
            new CandidateDiscovered(owner, name, classification, artistName, note)));
    // additionally:
    transactionTemplate.executeWithoutResult(status -> publisher.publishEvent(
            new RelationDiscovered(owner, artistId, /* from */ name, /* to (resolved later) */
                    classification, source.id(), note)));
}
```

In practice this is better modeled as **one event** (`RelationDiscovered`) that both the existing
`CandidatePersistenceListener` (creates the `Artist` node if it doesn't exist) and a new
`RelationEdgePersistenceListener` (creates/upserts the `artist_edge` row) subscribe to — that
avoids the two-events-must-both-land problem and keeps `ExpandUnitRunner` from needing to know
about catalog's edge storage. This is exactly the ADR-0022 event-driven pattern already in use
(publish inside a committing transaction; `@ApplicationModuleListener` durably delivers to
multiple subscribers) — no new mechanism, just a new event type and a new listener.

### Interaction with per-unit expand jobs (ADR-0023)

No conflict. `expand_job` is keyed on `(owner, artist_id, source)` — one row per "have we asked
this source about this artist." That's orthogonal to edges, which are keyed on `(owner, from, to,
type, source)` — "what did that ask produce." A single expand-job run can (and typically will)
produce zero, one, or several edges. The job model doesn't need to change at all; it's still
"drive the query," edges are "record what the query found," same relationship `expand_job` today
has to `CandidateDiscovered` events.

### Interaction with the review gate

This is the one real design question, and the issue is right to flag it. Candidates sit in
`PENDING_REVIEW` until a human approves or rejects them (ADR-0004). Two edges are involved in a
typical discovery:

1. `base_artist —[TRIBUTE_OF]→ new_candidate`, where `base_artist` is already `SEED`/`APPROVED`
   and `new_candidate` is brand new, landing `PENDING_REVIEW`.
2. In principle, a candidate could later be *discovered again* by expanding an already-approved
   artist that itself was reached through a still-pending one — cross-linking two nodes that are
   at different review states.

Recommendation: **write the edge unconditionally, regardless of either endpoint's review status.**
The edge is a record of what a source *asserted*, not an approval — provenance should be complete
even for rejected/pending nodes ("why did we ever suggest this" is a legitimate question to answer
for a *rejected* candidate too). What changes is **what queries surface**: traversal/ranking
queries that back the Candidates UI would filter `WHERE to_artist.status != 'REJECTED'` (or
similarly), the same way `ArtistRepository.findByOwnerAndStatus` already filters by status today.
The graph is the raw data; review status is a property of each node the graph is walked *through*,
not a constraint on what gets written into it.

### Modulith boundaries

The issue asks this directly rather than assuming an answer. Candidates, reasoned through
ADR-0021's module boundaries (`catalog`, `scan`, `expansion`, `settings`, `review`, `shared`):

- **A new `graph` module.** Clean separation, but premature: at this size the graph is *entirely*
  about artists (`artist_edge.from/to_artist_id` are FKs into `catalog.Artist`), has no
  independent lifecycle, and would immediately need either an event-based or direct-API
  dependency back into `catalog` for every query ("give me the artist for this edge"). A new
  module here mirrors the existing `catalog`/`scan` split (which exists because scan and catalog
  really do have independent lifecycles and failure modes) without a matching reason. This is the
  same shape of call the #95 review made for `shared.events` ("a dedicated `events` module is
  YAGNI" — see `docs/reviews/2026-08-13-phase-b-design-review.md`).
- **`catalog`-owned.** `artist_edge` rows reference `artist.id` directly, `Artist` is already the
  node type, and `catalog` already owns candidate persistence (`CandidatePersistenceListener`)
  and the grouped-candidates query support (`ArtistRepository.countByStatusGroupedByViaAndSource`,
  which is graph-shaped output today). Edge storage is a natural extension of what `catalog`
  already does: "own the artist entities and their metadata." **This is the better fit** —
  `expansion` stays a pure query-and-publish layer (per its own `RelationSource` Javadoc: "never
  writes"), and `catalog` remains the only module with write authority over artist-graph state,
  consistent with today's split.

Recommendation: **`catalog`-owned**, new `RelationDiscovered` event published by `expansion`
(mirroring `CandidateDiscovered`), consumed by a new `catalog.RelationEdgePersistenceListener`
alongside the existing `CandidatePersistenceListener`.

## 4. Migration path

**Backfill from existing `discoveredVia`/`source`/`note`:** partially possible, with real gaps.

What can be recovered:
```sql
INSERT INTO artist_edge (owner, from_artist_id, to_artist_id, type, source, note, created_at)
SELECT base.owner, base.id, a.id, a.source, /* source id unknown, see below */ '', a.note, a.created_at
  FROM artist a
  JOIN artist base ON base.owner = a.owner AND base.name = a.discovered_via
 WHERE a.discovered_via IS NOT NULL;
```

What's lost and can't be reconstructed, because the current model never captured it:

- **Which specific `RelationSource` (`musicbrainz` vs. `discogs`, both classified
  `MEMBER_EXPANSION`; `lastfm` vs. `similar-llm`, both `SIMILAR_EXPANSION`) produced the row.**
  `Artist.source` only stores the *classification* enum, not the source id. Backfilled edges
  would have to leave `source` blank/`"unknown-legacy"` or guess from the `note` text (fragile —
  `note()` strings are per-adapter but not guaranteed unique/parseable long-term).
  See `expansion/source/MusicBrainzRelationSource.java:30-32` and
  `expansion/source/DiscogsRelationSource.java:30-32` — identical `classification()`, different
  `note()` wording, is the only distinguishing signal today, and it's prose meant for a human,
  not a stable machine key.
  **Practical mitigation**: `note` text for MusicBrainz/Discogs both currently reads
  `"member/lineup relation of X"` — genuinely indistinguishable. Discogs vs. MusicBrainz specific
  source is *unrecoverable* from stored data as it stands. Last.fm vs. LLM-similar notes *do*
  differ ("via Last.fm" / "via LLM") and are recoverable with a string match.
- **Corroborating discoveries that were overwritten.** If artist X was discovered via
  `musicbrainz` first and `discogs` second, only the `musicbrainz` row (first writer) survives in
  `Artist` today — the `discogs` discovery event fired, hit the `existsByOwnerAndNameIgnoreCase`
  early return in `CandidatePersistenceListener`, and left no trace anywhere. There's no queryable
  history of it. It cannot be backfilled; it's simply gone.
- **Base-artist edges are name-matched, not ID-matched, and can silently misfire.**
  `discoveredVia` is a plain string; joining it back to `artist.name` for the same `owner`
  requires an *exact* name match. Any historical case where the base artist's name was later
  edited, or where `discoveredVia` doesn't exactly match any current `artist.name` row (e.g. the
  base artist was itself later merged/renamed, or was deleted), leaves an orphaned edge with no
  resolvable `from_artist_id`. Those rows would need to be dropped from the backfill or left as
  `NULL` (requiring the FK constraint to be nullable for backfilled data only — awkward).

**What stays:** `Artist.discoveredVia`/`source`/`note` should **not** be dropped even if edges are
introduced — see node-identity discussion below on why the flat "first-seen provenance" summary on
the node itself remains useful as a cheap denormalized default, independent of edges existing.
Removing them would be a separate, later decision once the edge table has proven itself, not part
of this migration.

**Practical read:** the backfill recovers *coarse* provenance (classification, base artist,
timestamp, note) for the *currently surviving* rows, but not the specific source id for the two
classifications that have two adapters each, and not any of the corroborating discoveries already
lost to the dedup short-circuit. This is a real, non-trivial gap — not a blocker, but going in
"clean-slate forward, best-effort backfill for history" is the honest framing, not "full
backfill."

## 5. Node identity

- **Artists are per-owner, matched by name.** `artist(owner, name)` is a unique constraint
  (`V1__baseline.sql:18`); there's no cross-owner artist identity at all today — two owners
  tracking "Radiohead" get two independent `Artist` rows with two independent ids. Edges, keyed by
  `(owner, from_artist_id, to_artist_id, ...)` and FK'd to `artist.id`, are automatically
  per-owner-scoped by inheriting that — no separate owner-scoping logic needed in the edge model.
- **Person-vs-band is not modeled today and the graph doesn't need to force it.** `MEMBER_EXPANSION`
  candidates (from MusicBrainz/Discogs) can be either — a band's related act *or* an individual
  member — and `Artist` has no `type`/`kind` column distinguishing them; a person and a band are
  both just rows with `source = MEMBER_EXPANSION`. The graph model doesn't need to solve this to
  be useful: `type = MEMBER_OF` on an edge already encodes "this relationship is a membership,"
  which is the information that matters for provenance/traversal, regardless of whether the
  `to_artist_id` node happens to be a person or a band. Adding a real person/band distinction on
  `Artist` (e.g. an `entity_type` column) is a legitimate future improvement but is **out of
  scope** for this spike — nothing in the issue's ask depends on it, and it's a orthogonal,
  separately-decidable change.
- **Name-matching to real nodes is the actual hard part, and it's not new.** Resolving a
  `RelationSource`-returned name (e.g. `"Thom Yorke"`) to an `artist.id` requires the same
  case-sensitivity/typo/alias handling `CandidatePersistenceListener` already grapples with today
  (`existsByOwnerAndNameIgnoreCase` is explicitly best-effort; see Finding D1 in the #95 review —
  the DB constraint itself is case-*sensitive*, so "Radiohead" and "radiohead" can coexist for one
  owner). An edge model doesn't make this easier or harder than it already is for `Artist`
  creation — `to_artist_id` resolution reuses exactly the same node-dedup path. It's worth noting
  explicitly, though, that a wrong match (treating two different real-world artists as "the same
  node" because their names happen to collide, or the reverse — the same artist landing under two
  slightly different name spellings as two nodes with no edge connecting them) would now corrupt
  graph traversal/ranking in a way it doesn't corrupt today's flat model (where each `Artist` row
  is independent and a bad match only ever means one bad `discoveredVia` string, not a
  polluted path other queries traverse through).
- **Reciprocal vs. directed edges: keep them directed, source-per-direction.** `TRIBUTE_OF` is
  inherently asymmetric (X is a tribute *of* Y, never the reverse) — directed is correct and the
  only sensible representation. `MEMBER_OF` is directional in a meaningful sense too (person →
  band, or band → related-band, depending on what the source actually returned) — MusicBrainz and
  Discogs relations aren't guaranteed symmetric round-trips (querying artist A may surface B
  without B's own lookup surfacing A, depending on how the source's relation graph is populated),
  so recording only what was actually asserted, in the direction it was asserted, is more honest
  than assuming symmetry. `SIMILAR_TO` is the one genuinely bidirectional-in-spirit relation
  (Last.fm/LLM "similar artists" is conceptually symmetric) — but even there, don't synthesize the
  reverse edge from nothing; if source `S` asserts `A similar-to B`, record exactly that one
  directed edge. If a later expansion of `B` independently has `S` (or another source) assert `B
  similar-to A`, that's a second, separately-provenanced edge — which is correct: it's a second
  real piece of evidence, not an artifact of the storage model. **Rule: never synthesize an edge's
  reverse; only store what a source actually returned.**

## 6. Scope/UX payoff and YAGNI check

**What concretely gets better if this is built:**

- Corroboration signal: an artist reachable via 2+ sources/edges becomes visible as such, which is
  real ranking material for the Candidates page ("suggested by 3 sources" vs. "suggested by 1").
  Today that signal is destroyed at write time by the dedup short-circuit.
- A genuine "why is X in my candidates" answer beyond one `note` string, including for a rejected
  candidate later revisited.
- A backing store for the grouped-by-base-artist × relation Candidates view that's actually
  designed for that shape, instead of a `GROUP BY` over flat columns that happens to produce it.
- Foundation for anything the issue mentions as future ("bands connected to X within 2 hops,"
  avoid re-asking a source it already knows the answer to) that is flatly **not achievable at all**
  in the current model, not just harder.

**YAGNI check — what this costs, and what's speculative:**

- One new table, one new event type, one new listener, one migration of `ExpandUnitRunner` (and
  every `RelationSource`) to also emit relation events. This is a moderate, contained change — not
  a rewrite — given how directly `RelationSource`'s existing shape maps onto an edge.
  Ballpark: comparable in size to the ADR-0023 per-unit job model work (new table + new event +
  new listener + one runner change), which shipped as a coherent PR.
  **This is a build-cost floor, not a full estimate — it doesn't include ranking/traversal UI,
  which is separately scoped below.**
- Nothing in the *current* product surface (the live Candidates review UI, show search, the expand
  job poller) requires multi-hop traversal or ranking today — those are explicitly *future*
  payoffs the issue names ("could power," "better ranking of candidates"), not things anything
  currently asks for. Building the storage layer now, with no consumer of traversal/ranking
  planned next, is the classic YAGNI tension: the model is *sound* and the cost is *contained*, but
  the concrete win today is narrower than "graph" sounds — it's really "don't discard corroborating
  discoveries" plus "a cleaner data shape for a view we already have."
- The corroboration/dedup win (not silently dropping the second source that finds the same artist)
  is real *today*, independent of any future traversal feature — that part alone has a
  standalone, non-speculative justification.

## 7. Go/no-go recommendation

**Go — conditionally scoped.** The relational edge table is a contained, low-risk addition that
fits the existing stack, module boundaries, and event-driven conventions exactly, and it fixes a
real, present-day defect (silent loss of corroborating discovery events) that has nothing to do
with speculative future graph features. That defect alone justifies the storage change.

**But scope the initial build narrowly**, to keep it honest against the YAGNI check above:

- **Build now:** the `artist_edge` table, the `RelationDiscovered` event +
  `RelationEdgePersistenceListener`, `ExpandUnitRunner` emitting it alongside
  `CandidateDiscovered`. This alone stops the corroboration loss and gives real provenance data to
  query, even manually/via `psql`, immediately.
- **Defer until there's a concrete consumer:** any traversal/ranking *feature* (multi-hop
  queries, "related bands" visualization, using edge count to sort candidates, skipping a
  re-query because an edge already exists). Build the recursive-CTE query and whatever UI/ranking
  logic needs it as its own follow-up issue, once it's clear what the first real consumer actually
  needs from the shape — don't speculatively build query/ranking machinery in the same change as
  the storage layer.
- **Explicitly not now:** Apache AGE, Neo4j, person/band entity typing on `Artist`, dropping the
  existing flat `discoveredVia`/`source`/`note` columns.

### Rough schema sketch

```sql
-- V10__artist_edge.sql (illustration only, not committed)
CREATE TABLE artist_edge (
    id             bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    owner          varchar(255) NOT NULL,
    from_artist_id bigint NOT NULL,
    to_artist_id   bigint NOT NULL,
    type           varchar(255) NOT NULL,
    source         varchar(255) NOT NULL,
    note           text,
    weight         double precision,
    created_at     timestamptz NOT NULL,

    CONSTRAINT artist_edge_from_fkey FOREIGN KEY (from_artist_id) REFERENCES artist(id),
    CONSTRAINT artist_edge_to_fkey   FOREIGN KEY (to_artist_id)   REFERENCES artist(id),
    CONSTRAINT artist_edge_unique UNIQUE (owner, from_artist_id, to_artist_id, type, source)

CREATE INDEX artist_edge_to_idx   ON artist_edge (owner, to_artist_id);
```

    String note

@Component
class RelationEdgePersistenceListener {

### Phased build outline (if greenlit)

1. **Schema + event + listener** (the "build now" scope above): `artist_edge` table (Flyway),
   `RelationDiscovered` event, `RelationEdgePersistenceListener` in `catalog`, `ExpandUnitRunner`
   emitting it. TDD per source adapter's `classification()`/`id()`/`note()` mapping. Best-effort
   backfill migration for existing `discoveredVia`/`source`/`note` data, explicitly scoped as
   partial per Section 4 (coarse provenance only, documented gaps).
2. **Prove it with a read-only query/tool**, not a UI feature yet — e.g. a debug endpoint or a
   `psql` query that answers "show me the edge history for artist X" — to validate the model
   against real data before building anything on top of it.
3. **First real consumer**, chosen once it's clear what's actually wanted: either surfacing
   corroboration count on the Candidates page (cheapest, most directly tied to the defect this
   fixes) or a 2-hop traversal query. Scope as its own issue, informed by what step 2 reveals.

## Concerns / open questions worth flagging before building

- The Discogs-vs-MusicBrainz `note()` collision (Section 4) means backfilled historical edges for
  `MEMBER_EXPANSION` will have an unrecoverable/guessed `source` id — worth deciding explicitly
  (leave blank vs. a `"legacy-unknown"` sentinel) rather than discovering it mid-migration.
- Section 5's directed-edge rule ("never synthesize the reverse") means a `SIMILAR_TO` relationship
  found only from one direction won't automatically show up when browsing from the other artist's
  side — that's a real, deliberate tradeoff for honesty of provenance, not an oversight, but worth
  the team explicitly agreeing to before it becomes a "why didn't X show up as related to Y"
  surprise later.

## Id strategy: UUID v7 considered, deferred (edges stay `bigint`)

We weighed UUID v7 for the edge PK and, more broadly, for every id.

- **The edge PK stays `bigint IDENTITY`** — consistent with every other table, and the edge's foreign keys reference `artist(id)` (a `bigint`) regardless, so a UUID edge id buys nothing the FKs can use. (The edge's real identity is its natural unique key anyway.)
- **Migrating all ids to UUID v7 is deferred.** The cost is high: a heavy populated-DB migration remapping every PK *and* every FK across ~6 interdependent tables on the live ~1,444-artist DB (add-uuid → backfill a v7 from `created_at` → parallel FK columns → swap PKs → drop old), plus entity/native-query/controller/test churn app-wide. The benefits (distribution / merge-safety, offline id generation, opaque public ids) aren't needs for this single-instance, single-DB, owner-scoped app — and v7's one real edge over v4 (index locality) is already what sequential `bigint IDENTITY` gives us.
- **Revisit only on a real driver** — a second instance/region, offline/mobile id generation, or a genuine need for opaque public ids. UUID v7 is the right choice *then*, generated via Postgres 18's native `uuidv7()` (prod/tests are on PG 16 today, so it'd be an app-side generator for now) as a deliberate migration.

(Mixed id types already coexist fine: Spring Modulith's `event_publication` table uses a UUID PK today while the domain entities use `bigint`.)
